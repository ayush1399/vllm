# Gemma4 + MTP profiling, 2026-11-01

The largest confirmed avoidable cost is uncaptured short prefill. Expanding
graph coverage reduces generation by 54–55 ms with unchanged model sources,
controlled acceptance and identical output hashes. The strongest kernel work
after that is removing collective staging copies, avoiding unnecessary draft
rows, reducing normalization traffic, and improving small-GEMM geometry.

At 20k/B4, initial plus mixed prefill occupies about 1835 ms of a 2154 ms
generation: **85% of total latency**. Pure decode is about 317 ms. The current
PDL path specializes fewer than 32 rows; the large prefill chunks use its
fallback. This explains why a substantial decode improvement has a small
effect on the long-prompt B4 total.

## Measurement scope

- Eight H100 80GB SXM GPUs, TP8, NVSwitch; real FP8-block target and assistant
  weights, BF16 activations/KV, FA4. Target has 60 layers and hidden size 5376;
  assistant has four layers and hidden size 1024.
- Optimized working tree at `7fd4e3584ec4fdc3acd59c3aef9ab2efeff1dd38`;
  source hashes in each result identify the uncommitted changes. Matched main
  is `5d55ef1590c92213e3893dc8e8712f7f2e0bc508` in an isolated checkout with
  its own freshly built core extension.
- Prompt lengths 128 and 20000, batches 1 and 4, output length 128. MTP k=4,
  **exactly two accepted drafts per verification** in every performance arm.
  Each request has 43 verification rounds, 172 drafts, 86 accepted drafts;
  acceptance histogram `[0, 0, 43, 0, 0]`.
- Prefix caching disabled; max sequence length 20160, batched token budget
  4096, max sequences 4. Normal capture ladder is 1–32 with
  FULL_AND_PIECEWISE graphs. The configured graph split limit is 32, but this
  FA4 path ignores that FA3 scheduling limit and selects its own splits.
- Nsight Systems node traces cover all eight ranks and all four complete
  generations on branch and main, including CPU sampling, NVTX, CUDA and NCCL.
  A second branch campaign uses graph-level tracing without CPU sampling.
  Torch traces cover all ranks and shapes with Python stacks and operator
  shapes, using 16 output tokens. Kernel-to-CPU-stage correlation maps 100% of
  kernels in all eight node traces.
- Nsight Compute separately profiles actual branch kernels on one H100 with
  ready local inputs, graph-node replay, cache flushing and 19 counter passes.

- Clean controls use three warmups and nine timed generations per shape,

  scheduler resume through completion is timed. Model sources are unchanged
  between controls. No production kernel/default changes were made for this
  profiling campaign.

### Profiler overhead

Do not treat trace gaps or summed collective durations as recoverable latency.
Node tracing raises branch generation from 334/357/717/2154 ms to roughly
396/426/868/2640 ms. Even graph-level tracing gives 360/388/781/2406 ms.
For short prefill the profiler even reverses the main/branch ordering.
CPU self times include instrumentation and native-call waits. GPU durations
below are per rank, usually the median across ranks; overlapping kernels are
not additive. Copy byte counts count memcpy payload, not both HBM reads and
writes. Only the clean controls establish end-to-end savings.

## 1. Short prefill runs outside useful graph coverage

**Confirmed, highest priority.** Capture sizes 1–32 cover verification but miss
the 128- and 512-row prompt forwards. Main also suffers this issue. The branch
adds opaque norm/GEMM wrappers whose eager CPU overhead contributes to its
short-prefill regression relative to matched main: about 67 vs 57 ms at B1,
and 66 vs 56 ms at B4.

| Prompt / batch | Current branch generation | Wider PW graph coverage | FULL, capture sizes through 512 |
| --- | ---: | ---: | ---: |
| 128 / 1 | 334.30 ms | 279.35 ms | 273.37 ms |
| 128 / 4 | 357.04 ms | 302.25 ms | 302.24 ms |
| 20000 / 1 | 716.97 ms | 725.73 ms | 723.17 ms |
| 20000 / 4 | 2153.60 ms | 2171.76 ms | 2163.94 ms |

The current column averages the two earlier process medians; each diagnostic
column is one new process median. The effect is much larger than run noise
for short prompts. Wide PW capture uses sizes 1–32 plus 64, 128, 256, 512,
1024, 2048 and 4096. Short initial prefill falls to 16.11/17.35 ms; decode
remains about 262/284 ms. All four wider-PW cases retain baseline output hashes.
FULL through 512 lowers B1 prefill further to 9.45 ms; **its short-B4 output
hash changes**, so it needs real rejection/quality validation before adoption.

The node trace shows why long collective durations can be misleading: the
121 short-prefill target reductions accumulate about 92.7 ms of rank-arrival
skew, while their total time after the last rank starts is only 1.8 ms.
This diagnostic includes profiler-induced skew and is not a 92.7 ms production
speedup claim. Torch attributes substantial eager work to attention launch,
GEMM wrappers, tensor allocation and argument validation. The clean graph
control establishes the actual improvement.

**Next:** cover common short-prefill shapes selectively. Avoid padding all
long-prefill tails to 4096 without measuring the extra GEMM work. Wider
coverage and FULL mode both slightly regress the 20k cases in these controls;
the precise long-case cause remains unproven.

Sources: `benchmark_gemma4_mtp.py` compilation config;
`vllm/v1/attention/backends/flash_attn.py` graph support and metadata builder;
`vllm/models/gemma4/nvidia/specialized_decode/{pdl,linear}.py` eager wrappers.
Evidence: `ablation-{graph-wide,graph-full-small}.json`, paired Torch traces,
and `branch.1.analysis.json` collective arrival statistics.

## 2. Prefill all-reduce copies every payload twice

**Confirmed traffic; savings still require a replacement implementation.**
`SymmMemCommunicator.all_reduce` copies GEMM output into a shared buffer,
reduces in place, then copies the shared buffer into an output tensor.

For 20k/B1, target prefill issues **1210 D2D copies per rank**, moving
**52.04 GB** of memcpy payload and taking **33.22 ms** in the trace. B4's
initial prefill plus mixed phase issues 4840 copies and moves **208.55 GB
per rank**, taking about **133.75 ms**. Actual HBM traffic includes a read
and write for each copy. These totals exclude assistant copies.

The SM90/TP8 FlashInfer fused-allreduce limit is 0.5 MiB. A target tensor with
128 rows is already 1.31 MiB, and a 4096-row tensor is 42 MiB, so prefill
falls into the staging-copy path. Decode uses the small-input FlashInfer path.
The fused communicator also caches a row limit derived from the first hidden
size; whether this unnecessarily rejects narrow assistant inputs needs a
runtime check.

**Next:** benchmark SM90 collective thresholds, and a CUTLASS epilogue that
publishes GEMM tiles directly into multicast mailboxes. The reduction should
write the consumer's required output directly. This removes a measured traffic
source; overlap alone leaves those bytes intact. Copy durations are an upper
bound on removable copy work, not a promised generation reduction.

Sources: `vllm/distributed/device_communicators/symm_mem.py:127`,
`flashinfer_all_reduce.py:468`, and
`vllm/compilation/passes/fusion/allreduce_rms_fusion.py:104`.
Evidence: `branch.{3,4}.analysis.json` copies and collective records.

## 3. Assistant computes rows that are subsequently discarded

**Zero-draft bypass measured; compact-path benefit not yet measured.** The generic
target-dependent speculator preserves the target's entire query shape to avoid
a host synchronization and reuse attention metadata. Its first assistant
forward therefore uses 5/20 rows during decode and 128/512/4096 rows during
prefill, then selects one row per request for sampling and feedback.

It also executes all four assistant layers on intermediate prefill chunks when
`num_speculative_tokens == 0`. `_prefill` checks `skip_sample` only after
running the model, with a comment about keeping drafter KV synchronized.
Gemma4 is Q-only and writes no assistant KV; it shares target KV instead.
The 20k/B1 trace contains five first assistant forwards (50 first-pass
reductions) rather than just one. The complete draft stage during these five
chunks sums to 41.84 ms on rank 0, including rank waits and the useful final
draft generation. That entire duration is not removable.

A diagnostic worker wrapper bypasses `propose` only when its explicit draft
count is zero, filling the expected draft output with -1. Compared with a fresh
unchanged-branch process using identical configuration and acceptance:

| Prompt / batch | Fresh branch | Bypass zero-draft assistant | Initial prefill change |
| --- | ---: | ---: | ---: |
| 20000 / 1 | 718.17 ms | 705.80 ms | 437.95 → 426.12 ms |
| 20000 / 4 | 2156.63 ms | 2141.65 ms | 449.87 → 436.83 ms |

All output hashes and acceptance histograms match, and timed monitored JIT
events are absent. This is about 12–15 ms lower generation latency in this
single-process pair. Short cases, where no intermediate chunk can be skipped,
vary by 2–3 ms between the processes; do not attribute that variation to the
bypass. The long-case prefill reduction is larger and decode stays within
about 0.5–0.7 ms. Real rejection/quality tests are still needed for integration.
Mixed batches that need drafts for an existing decode request cannot use the
whole-call bypass; compacting assistant rows is the larger remaining question.

**Next:** a Gemma-specific zero-draft bypass, then gather the selected row per
request on GPU before the first assistant forward. Build compact Q1 metadata
without `.item()` or host synchronization. Mixed batches, rejection positions
and shared-KV semantics need explicit validation.

Sources:
`vllm/v1/worker/gpu/spec_decode/target_dependent_ar/speculator.py:200`,
`:444`, `vllm/v1/worker/gpu/spec_decode/gemma4/speculator.py:48`, and
`vllm/v1/worker/gpu/model_runner.py:2157`.
Evidence: target/draft NVTX correlation, Torch input shapes, `branch.3.analysis.json`.
Clean controls: `ablation-{baseline-fresh,skip-empty-drafts}.json` and the
isolated benchmark's `gemma4_skip_empty_drafts` worker helper.

## 4. Small GEMMs leave much of the GPU unavailable or unused

**Confirmed resource and geometry limit; replacement speedup unmeasured.**
The PDL GEMMs use 232 registers/thread, allowing one resident CTA/SM. B1
gate/up has 84 useful output tiles, local QKV only 32, on a 132-SM GPU. Both
launch a persistent grid of 132 blocks; a full launch grid does not mean all
blocks perform useful matrix work. B1 uses a 16-row tile for five rows; B4
gate/up uses a 32-row tile for 20 rows.

NCU ready-input measurements: B1 gate/up 15.68 us, 1.91 TB/s HBM and 7.9%
achieved active-warp occupancy; local QKV 11.36 us, 0.98 TB/s and 8.6%.
Eligible warps per scheduler are only 0.13–0.17. Neither kernel spills registers.
In the actual short-B1 decode trace, PDL gate/up and QKV together account for
55.44 ms over 43 verification rounds, about 1.29 ms/round, before accounting
for overlap with their parent normalization kernels.

**Next:** test smaller output-column tiles, fewer staging buffers/registers,
or partition K for the narrow projection with an inexpensive reduction.
Measure the complete norm/GEMM chain with cold L2 and then TP8, including
any additional reduction cost. A CUTLASS/C++ implementation should address
tile count and weight-load latency, not just increase polling or overlap.

Sources: `specialized_decode/pdl_driver.cu`, `pdl_gemm.cuh`.
Evidence: `ncu-pdl{5,20}-gate`, `ncu-pdl5-qkv` reports and CSV exports.

## 5. Large-prefill normalization repeatedly moves FP32 residuals

**Confirmed bandwidth cost.** Target normalization/residual/quantization sums
to 56.43 ms for 20k/B1 and 226.02 ms across B4 initial plus mixed prefill.
The 4096-row kernel takes 92.32 us in NCU and moves data at 2.47 TB/s.
One 4096x5376 FP32 carry tensor is 88.1 MB; each boundary reads and writes
that carry alongside BF16 input and quantized output. This is substantial
necessary traffic under the current representation, rather than idle ALUs.

**Next:** keep residual state with the owner of a row tile and combine
reduction, residual updates, normalization and FP8/scales production. Compare
against the existing large-M kernel and include mailbox/broadcast traffic.
Preserve FP32 residual and BF16 intermediate semantics. The unsuccessful
small-row owner prototype does not establish the large-prefill result.

Sources: `specialized_decode/{model.py,full_chain.cuh,gemma4_full_chain.cu}`.
Evidence: `ncu-norm4096`, `branch.{3,4}.analysis.json`.

## 6. QKV preparation and KV-cache write remain separate

**Confirmed extra launch and tensor boundary.** Each target verification has
60 preparation kernels followed by 60 cache-write kernels. At short B1 these
sum to 9.24 and 5.86 ms over 43 rounds: about 0.215 and 0.136 ms/round.
During 20k/B1 prefill they cost about 10.1 and 7.8 ms respectively.

**Next:** write normalized/rotated K and V directly to paged cache in the
preparation kernel, retaining only Q as an intermediate. Handle slot mapping,
padding and both 256/512 head dimensions. The cache-write duration bounds the
removed standalone work; the fused producer still has to write the cache.

Sources: `specialized_decode/{attention.py,attention_prep.cu}` and
`vllm/v1/attention/backends/flash_attn.py` cache update.
Evidence: `branch.{1,3}.analysis.json`, `ncu-prep5`.

## 7. Remaining activation quantization passes

**Confirmed, smaller decode opportunity.** There are 61
`scale_1x128_kernel` launches per target verification: output projection inputs
plus the initial QKV input. They cost about 4.26 ms over 43 short-B1 rounds,
or 0.099 ms/round. Global QKV is already fed by the FP8 norm producer and
is not an additional quantization opportunity here.

Large-M GELU/down-projection still materializes BF16 activation and then
quantizes it, unlike the small-M fused GELU/FP8 producer. For 20k/B1, all
target quantization kernels sum to about 7.5 ms; GELU kernels add about 7 ms.
Those totals include more than just the removable activation round trip.

**Next:** have the attention output/combine epilogue emit FP8 plus group
scales, and extend GELU/FP8 fusion to large M with the required UE8M0 scale
layout. Validate exact BF16 rounding and reciprocal conventions.

Sources: `specialized_decode/activation.py:54`, `linear.py`, FA4 combine.
Evidence: `branch.{1,3}.analysis.json`; quantization is classified separately
from GEMMs even though its C++ namespace contains `gemm`.

## 8. FA4 graph splits use a static context bound, and the config knob is ineffective

**Confirmed execution and ineffective control; runtime tuning remains open.**
Target decode has 60 attention and 60 combine kernels per round. Combine costs
10.55 ms over 43 short-B1 rounds (0.245 ms/round).

The actual B1 replay grids are `(2,18,1)` for local attention and `(1,128,1)`
for global attention, at both short and long contexts. These represent 18 and
128 splits, respectively, not the configured 32. Graph capture uses a static
context bound, so short-context global attention still launches 128 splits.
Main uses 66 local splits instead of the branch's 18: the zero-window
correction **does affect the live runtime grid**. Earlier claims that a forced
32 bypassed the correction were incorrect. The trace does not isolate its
end-to-end benefit from the branch's other changes.

The `ablation-split1.json` control only changes
`flash_attn_max_num_splits_for_cuda_graph`. `FlashAttentionMetadataBuilder`
initializes `max_num_splits=0`, and only assigns the configured cap when
`aot_schedule` is true; here AOT scheduling is enabled for FA3, not FA4.
Consequently, the nearly unchanged 334/357/718/2156 ms results are a config
no-op, **not a negative performance result for unsplit FA4**. The configured
value recorded in worker metadata must not be mistaken for actual splits.

An actual six-value CUPTI sweep explicitly passes splits 1/2/4/8/16/32 to FA4,
times attention plus combine in a CUDA graph with cold L2, and checks relative
L1 error below 0.01 against split=1. Different shapes prefer different splits:
at short B1, local attention is 11.74 us at split=4 versus 12.58 at split=32;
global attention is 12.86 us at split=8 versus 19.10 at split=1. At long B1,
global split=1 takes 1105.63 us versus 57.58 us at split=32. These isolated
measurements are not model-level speedups. Additional sweep points cover the
actual runtime settings and heuristic selection, bringing the total to 80
shape/split measurements. At short B1, global split=128 takes 17.95 us versus
12.86 us at split=8. At long B1, split=128 takes 38.40 us versus 57.58 us at
split=32. A setting that helps short prompts can hurt long ones.

**Next:** tune FA4's actual selection or GPU scheduler metadata, with a
replay-safe context-dependent split count. Preserve parallelism on long
global attention and avoid excessive splits at short context. Fuse FP8/scales
production into combine where practical. A universal split=1 policy would
severely regress the isolated long-global case.

NCU's short local forward takes 12.13 us with 32 splits versus 14.24 us with
one, before combine; its grid shrinks from 64 CTAs to two. Global prefill
with 4096 queries and 16384 KV tokens takes 1512.70 us with 50.14% tensor-pipe
utilization, a different regime from decode.

Sources: `vllm/v1/attention/backends/flash_attn.py:707`, `:752`, `:855`, and
`vllm/vllm_flash_attn/cute/interface.py` split selection.
Evidence: actual grids in `branch.1.sqlite` and `main.1.sqlite`,
`fa4-split-sweep.json`, `fa4-split-sweep-extra.json`, and FA4 NCU controls.

## Useful work and limits

- The isolated 4096x5376x5376 gate/up GEMM takes 201.47 us and achieves 66.1%
  tensor-pipe utilization, approximately 1.18 PFLOP/s using `2*M*N*K`.
  It is a large cost but not evidence of gratuitous work. Improve communication,
  surrounding traffic and actual tile utilization before replacing it wholesale.
- Long-context B4 attention is more expensive than B1: target attention sums
  to 50.04 ms over 43 decode rounds versus 27.00 ms at short B1. Its useful
  KV reads and softmax work cannot be counted as automatically removable.
- Draft generation, target verification and rejection/sampling remain
  serially dependent at the round level. Local PDL overlap does not eliminate
  those dependencies.
- Do not add the opportunities in this report into a projected speedup.
  They overlap, and several lack a tested replacement. Controlled synthetic
  acceptance establishes performance comparability, not model quality.
